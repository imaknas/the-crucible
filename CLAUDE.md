# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Project Is

The Crucible is a multi-model AI arena: a full-stack app where users can run simultaneous conversations across OpenAI, Anthropic, Google and xAI models, branch the conversation tree from any checkpoint, pit models against each other (Arena Mode), invite a model to critically review a thread (Deliberation), synthesize divergent responses (Consensus Engine), and run autonomous multi-round structured debates between models with configurable stopping conditions (Debate Mode) — presented as an argument explorer for the user, not as a way to reach a trustworthy consensus.

## Commands

### Development (both services)
```bash
./start_dev.sh          # starts backend (port 8000) + frontend (port 3000), auto-resolves conflicts
```

### Backend
```bash
cd backend
uv sync                           # install dependencies
uv run python -m app.main         # start FastAPI server (reload enabled)
uv run pytest tests/ -q -n 4      # run all tests, 4 workers (pytest-xdist; ~10 s, serial ~16 s)
uv run pytest tests/test_graph.py -v   # run a single test file
uv run ruff check .               # lint
uv run crucible arena "prompt"    # CLI: run multi-model arena
uv run crucible debate "topic" -m gpt-5.4 -m claude-sonnet-5 --rounds 3   # repeat -m per model
uv run crucible --help            # every web UI capability has a command (tests/test_parity.py)
```

### Frontend
```bash
cd frontend
npm run dev      # Next.js dev server
npm test         # Jest tests
npm run lint     # ESLint
npm run format   # Prettier
```

### E2E (Playwright)
```bash
npm run test:e2e          # re-seeds the fixture DB, then runs the suite against a production build
E2E_DEV=1 npm run test:e2e   # against `next dev` instead (debugging)
npm run e2e:seed          # rebuild e2e/.fixtures/e2e.sqlite only
npx playwright test --repeat-each=3   # flake check
npx playwright show-report e2e/.report
E2E_BACKEND_PORT=8124 E2E_FRONTEND_PORT=3124 npm run test:e2e   # if 8123/3123 are taken
```
The frontend is built (`next build` + `next start`) into `frontend/.next-e2e` (`NEXT_DIST_DIR`), so a dev server in the same checkout is untouched; `next dev` compiled each route on its first visit, which made the first test to open a page slow or time out. `agenthub merge-branch` runs the project's test command from the platform registry (ruff, pytest `-n 4`, tsc, eslint, jest; not e2e).
`e2e/seed_db.py` builds a deterministic fixture by running the **real** LangGraph
workflow with a canned-response `ModelFactory` injected via `use_model_factory` — the checkpoints
have to be genuine because the tree endpoints walk LangGraph's own parent/child
links. Both servers run on ports 8123/3123 against that fixture (and `CHROMA_DIR`
under `e2e/.fixtures/`), so the suite never opens `backend/checkpoints.sqlite`
or `backend/chroma_db`.
- The backend runs with `CRUCIBLE_FAKE_LLM=1`: `default_model_factory()` is
  `app/llm/fake.ScriptedModelFactory`, which answers every registered model
  with a `ScriptedChatModel`. It streams
  "Scripted answer from <id> (<hash>)…" word by word, so `e2e/tests/live.spec.ts`
  can send messages and run whole debates; it reports its words as token usage,
  so replies get metrics and a cost. Prompt hooks: `[[slow]]` holds a
  stream open (10× delay), `[[fail:<model_id>]]` makes that model raise. Never
  set the variable outside tests.
- The fixture's "E2E Summarized Thread" is written with a 150-token `ThresholdPolicy` and `KeywordRecall` (no model call), so it has two summaries and replies with recalled excerpts: `e2e/tests/context.spec.ts` reads the summary marker, the reply's context note and the branch chip there.
- Live tests write real checkpoints, which is why the suite re-seeds on every run
  and each live test starts from **New Session**.
- One live test uses up a seeded fixture: "a debate interrupted by a server restart resumes…" resumes the seeded `E2E Interrupted Debate` (the harness can't restart its server, and nothing else interrupts a debate now), then skips until `npm run e2e:seed` runs again, e.g. on `--repeat-each`.
- With `reuseExistingServer`, Playwright silently tests against *whatever* holds
  the port. A stray `python -m http.server 8123` made every spec fail once; use
  the `E2E_*_PORT` overrides instead of killing processes you don't own.

## Architecture

### Backend (`backend/app/`)

**Layout: who does what**

| Layer | Where | Rule |
|---|---|---|
| Assembly | `main.py` | `create_app()` only: patches, lifespan (compiles the graph once, `checkpointer.setup()`), CORS, routers. No endpoints. |
| Transport | `api/*.py` | Parse/validate, call a service, shape the response. Routers get the graph via `Depends(get_graph_app)` (`api/deps.py`), never a global. |
| Behaviour | `services/*.py` | No FastAPI/WebSocket imports. `chat.py` (one chat turn: `build_turn_input`, `stream_turn`, `auto_title`), `debate.py`, `peers.py` (how debaters see each other), `synthesis.py` (the synthesis prompt and its framings), `convergence.py`, `arena.py` (arena and synthesis runs, the CLI/MCP entry points), `history.py` (a thread's tree, one path, search, the diff of two replies, deleting a branch), `uploads.py` (where files are kept and what text they hold), `keys.py` (provider keys in `.env`), `runs.py`, `live.py` (runs that outlive their socket: the run registry, below), `recall.py` (the default history recall), `context.py` (`ContextSettings`: a run's history choices), `tree.py`, `rag.py`, `message_format.py`, `textdiff.py` (what differs between two answers; pure, no `app.*` imports), `cases.py` (saved cases and their replays). |
| Models | `llm/` | The only place clients are built. Everything asks a `ModelFactory`. |
| Model policy | `registry.py` | Which models the app offers and the defaults (`MODEL_REGISTRY`, `FAMILY_META`, `display_name`, `model_color`). Read by every layer, so it imports no web framework; `api/models.py` only serves it. |
| Model facts | `catalog/` | What each provider model *is* (limits, capabilities, verified callable, web search works), built from first-party sources only. **Imports nothing from `app.*`.** |
| Compaction research | `compaction/` | When to summarize/prune and how much detail survives. **Imports nothing from `app.*`** (a test enforces it) so it can become its own project. |
| Persistence | `core/database.py`, `core/storage.py` | SQLite helpers; LangGraph owns its own checkpoint tables. Where everything is stored is a `Storage` the entry point chooses (below). |

**Chat transport — `api/chat.py`**
- `POST /chat` — one non-streaming turn: the same `turn_start` + `stream_turn` as the socket (Deliberation, `document_names`, `debate_session_id` included), answering the path messages and the turn's notices.
- `WebSocket /ws/{thread_id}` — `ChatConnection`: one run per model frame (owned by the run registry, below), streams `stream_start` / `stream_token` / `stream_end` (with the reply's checkpoint, path messages, `attached_documents`, `retrieved` sources, `notices` and `metrics`) / `stream_stopped` / `title_update` / `error`. `stream_start`, `stream_end`, `stream_stopped` and a model's `error` carry the `parent_checkpoint_id` that model forked from (the frontend's Retry reuses it) and the `turn_id`; `stream_start` carries `model_color`, the turn's `kind` and, for an ordinary turn, its `message`. **Every checkpoint id the backend hands out is the reply's tree node** (`chat.node_checkpoint`: the first of the run's checkpoints ending on that message), so an id from a reply, the tree, search or a path is the same id and deleting it deletes the reply. Where a frame forks is `arena.turn_start()` (below). Frames may name documents already kept for the thread (`document_names`) instead of sending their text. A frame with `type: "synthesis"` is a chat synthesis turn: `stream_turn(turn_kind=...)` tags its checkpoints (`runs.tag_turn_kind`, metadata `crucible_turn`), and the chat tree marks the reply as node `type: "synthesis"` / `metadata.kind`, the transcript message as `kind: "synthesis"` (`tree.is_synthesis_reply`). The prompt is the backend's: the frame names the replies in `answer_checkpoint_ids` and `arena.synthesis_request` writes the `INDEPENDENT` synthesis prompt, the same one CLI and MCP synthesis use; `build_turn_input(turn_kind=...)` flags the prompt message (`additional_kwargs.crucible_turn`) so `tree.is_synthesis_prompt` hides it in the tree, transcript and search (prompts written by the frontend before that are recognised by their marker sentence). Path messages carry `model_name` (display name). A disconnect cancels nothing: the runs belong to the server (below), every socket on the thread gets their frames, and `{type: "stop"}` from any of them stops every run on the thread (each sends `stream_stopped`). The first turn of an untitled thread is auto-titled from its prompt (never over an existing title: a debate titles its parent before the parent has a checkpoint). A frame with `debate_session_id` and no parent continues that finished debate: `debate.continue_from_debate()` writes the question and one record message (every round under its label, plus the synthesis) onto the parent at the checkpoint the debate started from (`debate_sessions.parent_checkpoint_id`), once per session (checkpoint metadata `crucible_debate`; the record message carries the same key in `additional_kwargs`, which is what `tree.is_debate_record` reads, shown as kind `"debate"`, model name "Debate"). Without it a turn after a debate started from nothing while the screen showed the debate. A frame with `join_turn` (a turn id, or one of its replies' checkpoints) adds its model to that answered turn ("+ model"): `arena.join_point` resolves the turn's question as it was asked (text, Deliberation, attached files, read from the question's checkpoint: the draft resets `is_deliberation` on the reply) and where it was asked from (on that reply's branch, else the turn's first reply's; the frame's `parent_checkpoint_id` pins another), and refuses a turn the thread lacks, a reply from before turn ids, a synthesis, and a model that already answered it (the socket also refuses one answering it now). The run gets the turn's id, so it is one more answer of that turn wherever turns are grouped, and its own `ChatTurn` (models: those that answered, then it), never the socket's current one; its frames carry `joins_turn: true`, and its `stream_start` and resume no `message` (the question is on the thread already). `POST /chat` takes `join_turn` too (`message` is then optional), as do `crucible arena|chat --join-turn` and MCP `invoke_arena(join_turn=)` (`run_arena(join_turn=)`: no prompt, Deliberation, attachments, debate or synthesis with it).

**Parallel runs — `services/runs.py`**
Any code that runs several graph invocations on one thread at once must go through these helpers:
- **Where a turn forks: `arena.turn_start()`.** A given `parent_checkpoint_id` (it must exist: `runs.fork_point` refuses one the thread lacks, which used to read back empty and start a conversation from nothing) or a finished debate's record pins every model there. With neither, **each model continues its own reply in the latest turn**: runs of one turn share a `turn_id` (`runs.tag_turn`, checkpoint metadata `crucible_turn_id`, on tree nodes and path messages), the head's turn names each model's reply, and a model with none (new, or it failed) continues the latest answer; threads from before turn ids fork everyone from the head. Models that answered side by side keep separate conversations instead of all continuing whichever reply finished first.
- **Pin the fork point.** Every model in a turn gets a pinned `checkpoint_id`. Unpinned concurrent runs resume from the thread head, i.e. from each other's half-written turns (B saw A's prompt; only one reply reached the head). `resolve_fork_point()` returns the head, or seeds an empty root checkpoint for a new thread. The head is `answered_head()`: when the newest checkpoint ends on the person's message (a turn cut off before any reply: Stop, a server restart, a failed model; or one still running, which a second tab then branches beside) it is the nearest ancestor ending on a reply, walking past that run's own `source: "input"` checkpoint, so the next turn is a sibling of the abandoned one instead of following it (the two messages used to reach the model merged). `GET /history` without `checkpoint_id` points the composer there too. The head also passes over a joining run's checkpoints (`runs.JOINED_KEY` / `is_joined`, set by `stream_turn(joins_turn=True)`): they are the newest but ask nothing new, and taking them as the head made the turn a model was added to the "latest" one. The WS handler resolves the turn's fork points once, in the receive loop, before any model writes, then hands each model's run to the run registry: frames that arrive while that socket's models are still running belong to that turn.
- **Tag the run.** `tag_run(config)` puts a run id in the config's `metadata`, which LangGraph copies into checkpoint metadata; `final_state_of_run()` finds the run's own last checkpoint. Re-reading the pinned config after the run returns the **parent**, which is what `stream_end` used to report.

**Runs outlive their socket — `services/live.py`**
A chat turn or a debate is a task the server owns, not the tab: a reload, a dropped socket, a closed tab or a second tab doesn't stop it. `RunRegistry` (one for chat turns keyed by thread, one for debates keyed by session: `LiveRuns` on `app.state.runs`, created in `main.lifespan`, reached through `Depends(get_runs)`) owns the tasks and, per key, the watchers. Connections hand it a run (`start(key, state, body)`) and watch the key (`watch` / `unwatch`); runs `emit` frames, which the registry delivers to every watcher by a plain call, never awaited: each connection queues them on its own `api/outbox.Outbox`, so a slow or vanished socket never holds up a model run.
- **Attaching.** Each live run keeps what it has emitted (its `RunState`: `ChatRunState` the text so far, `DebateRunState` the round in progress, the synthesis being written, the status and the run's `DebateControl`). A socket that connects first gets one coalesced frame per live run — chat `stream_resume {model, parent_checkpoint_id, turn_id, model_color, content_so_far, message, kind, turn_models}`, debate `debate_resume {status, round, question, answers, synthesis, convergence_score}` — then `attached` (chat `{runs: [{model, turn_id}]}`, debate `{live}`), sent on every connect so a client knows a reply it was showing has no live run, then live frames. Nothing is awaited between the catch-up frames and the subscription, so nothing is lost or doubled. Buffers die with the run; after it ends, the checkpoints are the record (`GET /history`, the transcript endpoint).
- **Ending.** Runs continue to completion after a disconnect, by design. Spend stays bounded without anyone watching: a chat run is one model call per model frame, and a debate stops at `MAX_ROUNDS`. What ends a run early: a stop from any socket (chat `stop`, debate `stop`, or a debate start/redirect/continue/synthesize, which cancel the session's live run first), a CLI or MCP caller cancelling its own call (Ctrl-C, a cancelled tool call: those runs are the caller's own, not the registry's), and the server shutting down — the lifespan cancels every run before the checkpointer closes, so a debate settles as `interrupted`. A server that died without shutting down is caught at the next startup (`db.interrupt_running_debates`). After any of these, `answered_head()` makes the next chat turn a sibling of the abandoned one.
- `db.claim_debate_session` stays the one-runner guard across processes (a server, the CLI, MCP); within the server the registry is the claimant.

**Network exposure**
The API has no authentication. The backend binds `127.0.0.1` unless `HOST` is set (the Docker image sets `0.0.0.0` and compose publishes ports on `127.0.0.1`). Because it trusts whoever reaches it, the guards in `api/security.py` stop other sites from reaching it *through the user's browser*; `create_app()` wires them (and takes `origin_policy` / `allowed_hosts` for tests):
- `OriginPolicy` is the one origin rule: localhost / 127.0.0.1 / [::1] on any port plus `CORS_ORIGINS`, never `*`. CORS reads it, and so does `WebSocketOriginGuard`, because CORS does not cover WebSockets: a handshake whose `Origin` is present and not allowed is closed with 1008 (browsers see a 403). No `Origin` (CLI, scripts, tests) passes.
- `TrustedHostGuard` answers 400 unless the `Host` header is localhost, 127.0.0.1, ::1, `testserver` (TestClient) or listed in `ALLOWED_HOSTS` (comma separated, `*` = any) — DNS rebinding makes an attacker's page same-origin, but its `Host` is still the attacker's name. Add the hostname the browser uses whenever the API is reached as anything other than localhost. It parses the header itself: Starlette's `TrustedHostMiddleware` splits at the first `:` and cannot match `[::1]:8000`.
- `SimpleRequestGuard` answers 403 to a POST whose `Content-Type` is missing, `text/plain`, multipart or form-urlencoded unless it carries `X-Crucible-Client`. Such a POST is a CORS simple request (no preflight), and FastAPI parses an untyped body as JSON, so without this any page could upload into a thread's RAG store or POST `/config/keys` from the user's browser. The custom header forces a preflight, which CORS refuses for foreign origins. The frontend sends it on uploads (`CLIENT_HEADERS` in `lib/api.ts`); JSON POSTs need nothing.
- `/config/keys` additionally rejects non-loopback clients unless `CRUCIBLE_ALLOW_REMOTE_CONFIG` is set. Writing keys is `services/keys.py` (shared with `crucible keys`): it rejects key values containing quotes, backslashes, whitespace or `$` so a value cannot add lines to `.env`, and leaves `.env` at mode 600. MCP has no key-writing tool: a key passed to a tool goes through the calling model's context.

**LangGraph workflow — `services/graph.py`**

The graph flow is: `summarize → (route) → [retrieve → grade_retrieval →] draft → metadata → synthesis → END` (`metadata` and `synthesis` are pass-throughs; `draft` is the turn's only call to the answering model)

- `summarize_history`: compresses history using the first of `SUMMARIZER_MODELS` with an API key (gpt-6-luna, then gemini-3.8-flash, then Haiku 5.5; chosen with recall on — luna's summaries alone keep little, it relies on recall) when the run's `CompactionPolicy` says so; non-destructive (appends a `PREVIOUS CONTEXT SUMMARY:` system message rather than removing messages). That message is `core/schema.summary_message()`, flagged `additional_kwargs={"crucible_summary": True}`; everything that looks for a summary (sanitizer, `context_snapshot`, chat/tree/history display, MCP) uses `is_summary_message()`: system role only, the flag, or — for summaries written before it — text *starting* with the marker. Never match the marker anywhere in the text: user messages and attached documents (which sit in the drafting system prompt) can quote it (`tests/test_summary_marker.py`). `drafting_node` asks the same policy whether this call sees the raw history or jumps to the summary.
- **Compaction policy** (`app/compaction/policy.py`): `ThresholdPolicy` (default: the model's registry `limit`, i.e. the original behaviour), `NeverCompact`, and pluggable thresholds (`fixed_tokens`, `fraction_of_limit`). Inject per run with `config["configurable"]["compaction_policy"]`; the graph passes it a `ContextSnapshot` (token/message counts) and a `ModelBudget` (model facts). Re-summarizing waits for new material: due when summary + newer messages pass the threshold, but never before `min_new_fraction` (0.5) of the threshold is new — a summary larger than the threshold used to re-trigger on every eligible turn. `config["configurable"]["summarizer_model"]` overrides which model writes the summary (default: `default_summarizer()`, the first of `SUMMARIZER_MODELS` with a key; the Control Panel's Summarizer choice arrives here through `ContextSettings`), and `config["configurable"]["summary_instruction"]` what it is asked to write (a `SummaryInstruction` from `app/compaction/instructions.py`; default `DetailedBrief`, the original prompt; `LengthTarget(tokens)` adds only a length limit; `HandoffBrief` is Codex CLI's compaction prompt). What stays verbatim once history is pruned is a `Retention` (`app/compaction/retention.py`) injected as `config["configurable"]["history_retention"]`: `KeepRecent(5)` by default (the verbatim window below), `KeepUserMessages(budget)` keeps every user message within a token budget as Codex CLI does.
- **History recall** (`services/recall.py`): once history is pruned, a `HistoryRecall` (`config["configurable"]["history_recall"]`) picks hidden original messages relevant to the latest request and shows them again as request notes, so the summary is never the only copy. The app's default is `GuidedRecall` with a `ModelRewriter` on the first of `RECALL_MODELS` (`registry.py`) that has a key — attached by `with_default_recall()` where runs start (`chat.stream_turn`, `POST /chat`, `arena.run_arena`, debate rounds and synthesis), **not** as a graph fallback, so experiment configs get only what they name. It costs nothing until a thread compacts, then one small model call per turn. A recall failure is logged and the turn continues. The rewriter's call is tagged `INTERNAL_TAG`; every `astream_events` consumer passes `exclude_tags=[INTERNAL_TAG]`, or its search terms stream into the reply (`tests/test_recall_default.py`).
- **The verbatim window** (`KEEP_VERBATIM` = 5 in `graph.py`): the newest messages are left out of a summary and must stay visible verbatim on *every* later turn, and be folded into the *next* summary. Both used to fail — recovery ran only on the turn the summary was written, and re-summarizing started at the previous summary — so those messages ended up in neither the summary nor the context. `tests/test_compaction.py` guards both.
- `retrieve_node` / `grade_retrieval_node`: RAG path, only active when `use_rag` toggle is on; retrieves from ChromaDB then LLM-grades each chunk for relevance. It searches the run's document thread (`documents.document_thread`: a debate lane reads the parent thread's files, where uploads are indexed; it used to search the lane and find nothing). The retriever is `config["configurable"]["retriever"]`, else `rag.retrieve_context`, which raises on failure: the node turns it into a turn notice instead of answering as if the thread had no documents.
- **What a turn was written from is visible.** `drafting_node` stamps the reply with `crucible_context` (`message_format.CONTEXT_KEY`, read by `reply_context()`): tokens sent, the model's soft limit and window, whether it jumped to the summary (`pruned`, `kept_verbatim`, `hidden`) and the excerpts recall brought back (`recalled`, filled through `sanitize_messages(trace=)`). Path messages and tree nodes carry it as `context` (null for older replies). A summary on a path is a marker, not hidden: `tree.summary_entry` (role `system`, kind `summary`, `id` `summary-<checkpoint>`, no `checkpoint_id`, text without the marker sentence); the chat view draws it as `SummaryMarker` and leaves it out of the scroll map. `graph.next_turn_context` / `history.context_report` say what the next turn from a branch point would send each model, with the same policy decisions the turn makes (approximate: one tokenizer, before the new message, recall and attachments): `GET /history/{thread}/context?checkpoint_id=&models=`, `crucible context`, MCP `get_thread_context`.
- **Notices.** What degrades a turn without failing it (a summary that couldn't be written, retrieval that failed) is appended to the turn's `notices` state (reset by `build_turn_input`) and reported on `stream_end`, the CLI and MCP. The grader is `config["configurable"]["grader_model"]`, else `default_grader()` (first of `GRADER_MODELS` with a key), else the answering model — always built with **no toggles** (no web search bound) and called with `INTERNAL_TAG`. It used to be the answering model with the turn's tools, once per chunk.
- `drafting_node`: the core generation node. Handles Deliberation mode (wraps all history with `[Model]: ...` attribution), RAG context injection, attached documents, native web search via `bind_tools` (the only toggles the backend reads are `use_rag` and `use_web_search`), and `sanitize_messages` for context pruning
  - **No persona by default.** Models get no system message unless something needs one: the run's own system prompt (`config["configurable"]["system_prompt"]`, set from `ContextSettings.system_prompt`), the Deliberation critic role (after the person's prompt), or RAG / attached-document context, joined in that order. The app used to send an "academic research assistant" persona plus a request to end every reply with a self-assessed confidence in `<metadata>` tags; Arena then compared models under a persona the app chose, the confidence was never shown (and verbalized confidence is poorly calibrated), and the request may have tripped an OpenAI reasoning-model prompt filter. Don't add a default instruction back without a baseline it beats (see `scaffold_audit` below). `extract_text` still strips `<metadata>` blocks from older replies.
- `synthesis_node`: a pass-through kept so existing checkpoints still replay (and `resolve_fork_point` seeds roots `as_node="synthesis"`). It used to call the turn's own model, tools bound, after every reply to rewrite a rolling `current_thesis` no client displayed: one paid call per model per turn, delaying `stream_end`. Old checkpoints still carry `current_thesis`; nothing reads it, and the MCP `thesis` fields are always `null`. Cross-model synthesis is always an explicit run (`arena.py`, `debate.py`).
- `metadata_node`: a pass-through kept so existing checkpoints still replay. Its old write to `node_metadata` never ran (a node's config has no `checkpoint_id`). Models are no longer asked for a confidence and nothing parses one; older databases keep their unused `node_metadata` table, which is no longer created, and `GET /graph/{thread_id}/topology` returns an empty `metadata` per node

**Model registry — `registry.py` (policy) and catalog — `app/catalog/` (facts)**
`MODEL_REGISTRY` is *policy*: which models the app offers, their display names, soft `limit`, `native_search`, defaults, legacy entries. `FAMILY_META` maps each family to its label, colour and `env_key`, and everything per family derives from it: `/models` groups by it (and ships `env_key`, `color` and the backend's `limits`), `keys.KEY_NAMES`, `registry.model_color` (the CLI and the debate tree), so a family needs no edit elsewhere. A family may have no models (a new provider before its first model is verified): `/models` still lists it with `models: []`, the Control Panel's API Keys section takes its key, and the model picker leaves it out.
The catalog is *facts*, committed as `app/catalog/data/catalog.json` and refreshed with `uv run crucible catalog-sync`:
- Sources are first-party only — no LiteLLM / models.dev. Each provider is a `ProviderSource` strategy (`catalog/sources.py`): the providers' own `/models` endpoints (Anthropic and Google report limits and capabilities; OpenAI only ids; xAI's `/v1/language-models` reports modalities, aliases and reasoning efforts, joined with `context_length` from its `/v1/models`, a window shared by input and output, with no output limit), OpenAI's own docs pages for OpenAI context windows (window − max output), and `data/overrides.json` for anything else, each value with a `source`.
- Every model is probed with a real minimal call (chat, then web search). OpenAI ids that 404 on chat/completions are retried on the Responses API (LangChain routes several "-pro" models there) and recorded as `capabilities.api`. Timeouts, 429 and 5xx are *inconclusive*: never a verdict, retried next sync; an inconclusive result keeps an earlier success but clears an earlier failure. `--probe new|failed|all|none`.
- Error text is committed: account identifiers (`org-…`) are redacted in `sources._redact`.
- Prices (`catalog/prices.py`, `data/prices.json`) are hand-kept from the providers' pricing pages — no API exposes them — each entry naming its page, with dated changes (`until` / `after`) for introductory prices. `PriceBook(prices, day)` resolves dated snapshot names ("gpt-5.4-nano-2026-03-17") and prices a LangChain `usage_metadata`, cache reads included. Never assume a model is cheap from its name: `gpt-5.4-nano` costs twice `gpt-6-luna`, and `gemini-3.5-flash` is the most expensive Flash.
- `tests/test_registry_catalog.py` fails if the registry offers a model the catalog hasn't verified, or claims `native_search` the probe disagrees with — that is the signal to run `catalog-sync` or fix the registry.
- **A provider can answer an id with another model.** Google routes retired ids to their replacement and the call still succeeds (since late 2026-10, `gemini-3.5-flash` is answered by `gemini-3.6-flash` and `gemini-3.7-flash` by `gemini-3.8-flash`; the deprecations page at aistudio.google.com/docs/deprecations says which). The chat probe records the model the response names (`model`, or Google's `modelVersion`) as `verification.served_as` when it is neither the id nor a dated snapshot of it (`sync.routed_to`), and `test_registry_catalog` refuses to offer such an id except as Legacy. Replies are priced as the model the provider says answered when the price list knows it (`metrics.message_metrics`).
- `graph.model_budget()` takes `context_window` from the catalog, the soft limit from the registry.
- Anthropic web search: `web_search_20260209` needs programmatic tool calling, which models without `code_execution` (Haiku 4.5) reject with a 400; `anthropic_web_search_tool()` adds `allowed_callers=["direct"]` for them (and for unknown models). The app provider and the catalog probe share it.
- **xAI** (`XAIProvider`, `XAISource`, langchain-xai): xAI calls Chat Completions legacy and offers its tools only on the Responses API. Plain turns use chat/completions (ChatXAI's default; it turns `stream_usage` on itself and adds reasoning tokens to `output_tokens`); web search binds xAI's `{"type": "web_search"}` (`XAI_WEB_SEARCH_TOOL`, shared with the probe), which makes langchain-openai send the request to `api.x.ai/v1/responses`. The chat probe tries chat/completions, then the Responses API on a 404, recording `capabilities.api`; a model recorded as `responses` is built with `use_responses_api`. Per-request notes are split off like OpenAI's (`split_request_notes`, as a system message): xAI caches the longest run of leading messages that match exactly. UUIDs (xAI's team ids) are redacted from probe errors, and an error body may be a bare JSON string (`_probe` reads both). Offered (verified 2026-11-02 by `catalog-sync`, chat and web search): `grok-4.7` (Flagship, also in `REFEREE_MODELS`, so it writes the argument map of a default three-family debate), `grok-4.3`, `grok-4.20-0309-non-reasoning`. Their soft `limit` is 140k: xAI bills the whole request at double the rate from 200k prompt tokens, and `PriceBook` has one price per model (the <200k one). Prices from https://docs.x.ai/developers/pricing (source `xai`; the listing's `prompt_text_token_price` / 10,000 is USD per 1M tokens, a cross-check, not the source); register the catalog **id**, not an alias (`capabilities.aliases`). Checked with a real turn through the app, plain and with web search; not yet with request notes (recall) on the Responses path, where they go as a trailing `system` item.

**Model construction — `llm/`**
- `providers.py`: one `ChatProvider` strategy per family (`create(model_id, api_key)`, `with_web_search(llm)`; `ProviderModelFactory` passes the key from the `env` it checked, so an injected `env` is the one used), registered in `PROVIDERS`. Nothing else branches on the provider.
- Gemini requests carry **no `temperature` / `top_p` / `top_k` and no `thinking_budget`**: the upcoming Gemini models reject them, and `langchain-google-genai` (still true in 4.4.0) injects `temperature=1.0` for every Gemini 3+ id, so `GoogleProvider` builds a subclass that drops the three sampling fields (`tests/test_google_provider.py`, `tests/test_upstream_hooks.py`). Thinking depth is `thinking_level` only (`minimal|low|medium|high`; experiments bind it with `model@level`). Don't add sampling or budget parameters to a Google client.
- `factory.py`: `ModelFactory` protocol. `ProviderModelFactory` (real; registry, providers and env are constructor-injectable), `CallableModelFactory(fn)` (tests/scripts), `has_credentials()` (the one key check). Graph nodes call `model_factory_from(config).chat(model_id, toggles)`: a run may inject `config["configurable"]["model_factory"]`, otherwise `default_model_factory()` — the real providers, or `llm/fake.ScriptedModelFactory` under `CRUCIBLE_FAKE_LLM`. `use_model_factory(f)` overrides the default for a block (tests, `e2e/seed_db.py`).

- **Verify any ID before adding it.** Presence in a provider's `/models` listing is not sufficient — some listed IDs are not chat models. `gpt-5.4-pro`, `gpt-5.5-pro` and `gpt-5-pro` 404 on `v1/chat/completions`, and `gemini-3-flash-lite-preview` no longer exists; all shipped in the registry as broken entries. Confirm with a real one-token completion (`catalog-sync` does it). xAI also lists aliases (`grok-…-latest`) beside each id; register the id.
- `limit` is a **soft** threshold that triggers summarisation in `get_token_limit()`, not the hard API window. Anthropic values are 70% of `max_input_tokens` from `GET /v1/models/{id}`.
- `DEFAULT_MODEL`, `DEFAULT_ARENA_MODELS`, `SUMMARIZER_MODELS`, `RECALL_MODELS` and `GRADER_MODELS` live here and are the only copies; helper models are picked from a list with `llm.factory.first_offered_with_key()`. `GET /models` returns `default_model`/`default_arena_models`/`default_summarizer` so the frontend does not hardcode one — a previously hardcoded frontend default is how it drifted onto a legacy model (the selection is seeded in `useModelCatalog` from `default_arena_models`, filtered to families with a key, and persisted as `crucible_selected_models`: `lib/modelSelection.resolveSelection`; the Parameters toggles persist through `useToggles`).
- Entries marked `"desc": "Legacy"` are retained because existing checkpoints reference them; removing one breaks replay of those threads.

**Message sanitizer — `graph.py:sanitize_messages()`**
Critical function called before every LLM invocation. Ensures non-empty content, merges consecutive same-role messages, enforces alternating human/AI turns (Anthropic requirement), handles the summary-jump pruning, and caps total chars at 1.2M.

**State schema — `core/schema.py`**
`CrucibleState` TypedDict: `messages`, `current_thesis` (legacy, unused), `active_peer`, `toggles`, `parent_id`, `branch_name`, `is_deliberation`, `retrieved_chunks`, `attached_documents` (filenames in this turn's context), `documents` (legacy content; new turns write `{}`). See attached documents below.

**Attached documents — `services/documents.py`**
A frame's `documents` are exactly the documents in that turn's context: a turn sent without any has none, and a removed attachment is gone from the next turn. Only their **filenames** go into the turn's state (`attached_documents`); the content is saved in `thread_documents` (`ThreadDocumentStore`, keyed by thread and filename). In state, every checkpoint of a turn (4-6 per model) stored the full text again, up to 10 MB a file. Entry points call `names = await attach_documents(config, documents)` and pass the names to the turn input (`chat.stream_turn` / `build_turn_input(document_names=...)`, `POST /chat`); saving is idempotent, and a file re-sent with new content replaces the stored one (a later turn naming it sees the new content). Debates store the start frame's documents once, for the parent thread, and every round of every participant names them; the sub-thread runs read the parent's copy through `config["configurable"]["document_thread_id"]`. `ContextSettings.apply()` puts the store on the run config (`config["configurable"]["document_store"]`, via `with_default_documents`), and `drafting_node` reads `documents_for_run(state, config)`: legacy `state["documents"]` content plus the named files from the store. A run that names no store sees only content in its state.

**Persistence — `core/database.py`**
SQLite at the run's `Storage.db_path` (`backend/checkpoints.sqlite` unless `DATABASE_PATH` says otherwise).
- **Storage is chosen by the entry point** (`core/storage.py`): a `Storage` (database, upload directory, Chroma directory, `.env`) built with `Storage.from_env()` by the server (`create_app(storage=...)`, kept on `app.state.storage` and set for every request and socket by `StorageMiddleware`), the CLI and the MCP server at startup, `e2e/seed_db.py`, and per test by `conftest`. Code that stores asks `current_storage()`; a context nobody set one for raises `NoStorage` rather than falling back to the app's real database. Tasks, `asyncio.to_thread` and LangChain's executor-run nodes inherit it; a raw `threading.Thread` doesn't (use `contextvars.copy_context().run`). The compaction harness points its runs elsewhere with `set_storage(replace(current_storage(), db_path=...))`; it used to rewrite a module global. Stores `thread_metadata` (title), `node_positions` (x/y for React Flow canvas), `node_metadata` (confidence, conflict; nothing writes it) and `thread_documents` (attached documents per thread and filename; created by `init_db()`). LangGraph uses the same SQLite file for its own checkpoint tables via `AsyncSqliteSaver`.
- **Write from async code only through `asyncio.to_thread`.** The helpers are blocking `sqlite3` calls, and `AsyncSqliteSaver` resumes on the event loop between a checkpoint INSERT and its commit; a helper write run on the loop in that gap waits for a lock that cannot be released until the loop is free, so it fails after the 5 s busy timeout with "database is locked" (the lost auto-titles), stalling every stream meanwhile. `tests/test_db_off_loop.py` reproduces it and guards the chat, REST and debate paths. Reads are safe under WAL (set by the saver's `setup()`).
- `list_threads()` orders by recent activity: the newest checkpoint on the thread or any `{thread_id}::*` sub-thread (LangGraph checkpoint ids are UUIDv6; `checkpoint_time()` reads their timestamp), else its newest debate's `created_at`. Ordering by thread id, which is random, put a new thread anywhere in the sidebar. An untitled thread's `title` is `None` there; `services/threads` names it (below).
- Deletes cascade: `delete_thread_data()` also removes every `{thread_id}::*` debate sub-thread (stored documents included) and the `debate_sessions` rows; `delete_debate_session()` removes exactly the session's own stored threads (`session_thread_ids`), keeping any another session on the parent still names (legacy sessions share theirs). Sub-threads are matched by `substr(thread_id, 1, ?)`, not `LIKE`, because thread ids contain `_`.
- `debate_sessions.round_scores` is a JSON object of `{round: score}`, written by `record_round_score()` so the per-round stability score survives a page reload. Added by migration in `init_db()`.
- `saved_cases` and `case_replays` (services/cases.py) are the one thing **not** deleted with a thread: a case copies its turn whole, so its source thread and turn ids are a reference only, and a replay's row copies its answers, so it outlives the thread it ran in. Deleting a case deletes its replay rows, never the replay threads (ordinary threads). Don't add them to `_purge_thread_rows`.

**RAG — `services/rag.py`**
ChromaDB persistent vector store at `backend/chroma_db/`. Local HuggingFace embeddings (`all-MiniLM-L6-v2`). Documents are indexed per `thread_id`.
- Re-uploading a file replaces its chunks (`rag.index_document` deletes the thread's chunks of that filename first). An upload is also kept as an attachable document for the thread (`uploads.keep_upload`; the route stores it before answering, so the next frame can name it), and the route parses PDFs off the event loop.
- Uploads are stored under `uploads/<sha256(thread_id)[:32]>/` (the id comes from the client, so it is hashed, never used as a path) and indexed with `thread_id` metadata. `services/uploads.py` checks a file (type, 10 MB), saves it and extracts its text (`save_upload`; `upload_file` for a local path, with the indexer injected) for `POST /upload`, `crucible upload` and MCP `upload_document`; `read_documents` turns local files into a turn's attached documents (`--attach`, MCP `attachments`) with the same checks.
- Deleting a thread goes through `services/threads.ThreadDeleter` (both `DELETE /threads/{id}`, via `Depends(get_thread_deleter)`, and `crucible threads --delete`): RAG chunks (`rag.delete_thread_chunks`, a metadata delete on the raw collection that never loads the embedding model), the thread's upload directory, then `delete_thread_data()`. External stores go first so a failure leaves the thread listed for a retry. Tests inject a fake collection / override the dependency; never the real store. Files uploaded before per-thread directories sit flat in `uploads/` and are not tied to any thread.
- `get_vector_store()` / `get_embeddings()` are lazy singletons behind a lock (the Chroma client is its own singleton, shared with deletes). Graph nodes are sync and run on executor threads, so parallel models hit them together; two concurrent `PersistentClient` inits fail with "Could not connect to tenant default_tenant". The directory is the run's `Storage.chroma_dir` (`CHROMA_DIR`), with one client and store per directory.

**Tree reconstruction — `services/tree.py`**
Walks LangGraph checkpoint parent-child links to build a deduplicated conversation tree for the React Flow canvas.
- `load_thread_states()` pulls every checkpoint state for a thread in a single `aget_state_history` pass (with a per-checkpoint fallback for branches outside the main lineage). Use it instead of looping `aget_state` — LangGraph writes 4-6 checkpoints per turn, so the loop was hundreds of round trips per tree fetch.
- `deduplicate_checkpoints()` merges sibling checkpoints with the same key (`get_content_key`): the person's question, written once per model's run, merges by its text; a reply's key is its message id, so two models that answer alike ("Red") stay two nodes. Keying replies by text dropped all but one of them from the tree, and from the compare cards after a reload.
- `build_significant_forest()` collapses pass-through checkpoints (synthesis prompts, summarisation) so each significant node is re-parented onto its nearest significant ancestor.
- `tidy_tree_layout()` is a Reingold-Tilford style layout: one column per leaf, each parent centred over its children, computed iteratively so deep threads can't blow the stack. Positions saved via `node_positions` override it per node without shifting siblings.

**CLI and MCP: everything the web UI does, through the same services**
`tests/test_parity.py` maps every HTTP route, debate socket command and chat-frame field to a CLI command/option and an MCP tool/argument, and fails when one has no entry (exceptions: canvas node positions, and writing keys over MCP). A capability that existed only in a route handler or the frontend was the gap: deleting a branch, search, uploads and keys used to live in `api/*.py`, the chat synthesis prompt in the frontend, and arena turns had their own copy of a turn without documents, Deliberation or a branch point. So the behaviour goes in `services/`, and the three transports call it.
- **One turn runner.** `chat.stream_turn` is every turn: the socket, `POST /chat`, arena (`arena.model_turn`), synthesis, debate rounds and the debate's argument map. It yields `token`, `drafted` (the reply is written; later nodes are bookkeeping) and one `end`. Don't add another `astream_events` loop.
- **Per-answer metrics** (`services/metrics.py`). `drafting_node` times its model call with a `ReplyTimer` on the call's own callbacks (first visible token, end; clock injectable as `config["configurable"]["monotonic_clock"]`) and stores `{ttft_ms, total_ms}` on the reply (`additional_kwargs["crucible_timing"]`), so it is in the checkpoint like the reply; tokens are the reply's `usage_metadata` (OpenAI streams usage by default, Anthropic and Google always). `message_metrics(msg, day=…)` is the one reader: `{ttft_ms, total_ms, input_tokens, output_tokens, reasoning_tokens, cached_input_tokens, cost_usd}`, priced by `PriceBook` on the day the checkpoint was written, `cost_usd` null for an unpriced model (never a guess), the whole object null for a reply that recorded neither (older ones). `end`, path messages (`metrics`), tree nodes (`metadata.metrics`), `compact_tree`, arena and synthesis answers carry it; times cover the model's call, not summarizing or retrieval before it.
- `services/arena.py`: `open_graph()` (compiled graph on the SQLite checkpointer, as a context manager), `resolve_models()` (validation + key check, raises `ValueError` with a caller-facing message), `turn_start()`, `run_arena()` (parallel answers, optionally a Deliberation turn, which needs a conversation, with attached documents; then an **explicit** synthesis call hung from the question the answers share, `question_point()`, as the web UI's does — the legacy per-model `current_thesis` in old checkpoints is not a cross-model synthesis and must not be presented as one), `synthesize_thread()` (by default the answers to the latest question, `latest_turn_answers()`, syntheses left out; or exactly `checkpoint_ids`, from any branches; synthesizer defaults to the first answer's model; it hangs from the first answer's question), `synthesis_request()` (the one prompt writer for every mode, below), `answer_components()` (a checklist's parts: a helper call, nothing written), `list_models()` (with `native_search`, the catalog's context window and today's `price_per_mtok` from `catalog/prices.py`).
- **Synthesis modes** (`synthesis.SYNTHESIS_MODES`, framings picked by `synthesis_framing()`): `merge` (one answer, `INDEPENDENT`), `compare` (a table of where the answers differ, `COMPARE`: no merged answer, no winner), `checklist` (one answer from the parts the reader kept, `checklist_merge(keep)`; the parts come from `answer_components` / `POST /synthesis/components`, parsed by `parse_components`, and a reply in another form is an error, never an empty list), `ask` (the reader's question about the answers, `ask_about`). Answers to different questions are each shown with theirs, and a model appearing twice is numbered (`arena._labelled_answers`). The reply records its mode and question (`runs.SYNTHESIS_MODE_KEY` / `SYNTHESIS_QUESTION_KEY`, in checkpoint metadata and the prompt message via `stream_turn(turn_note=)`); tree nodes and path messages carry `synthesis_mode` / `synthesis_question`, and the UI labels the reply by it (`lib/synthesis.synthesisLabel`). Chat frames: `synthesis_mode`, `keep_components`, `synthesis_question`; CLI `synthesize --mode/--keep/--question` (checklist without `--keep` lists the parts); MCP `synthesize_answers(mode, keep, question)`, `list_answer_components`.
- **Saved cases** (`services/cases.py`): a turn copied whole so it can be re-run on today's models (the habit `scaffold-audit` and `catalog-sync` have: re-measure when models change). `save_case(thread, turn)` takes the turn id or one of its replies' checkpoints (`votes.turn_answers`) and copies the question; the messages before it **as the graph held them** (`messages_to_dict`) on the branch of the reply named, else the turn's first answer (`history_from`; turn-mates continued their own conversations, so their histories differ); the attached documents' content (`ThreadDocumentStore`) and, when document search was on, every file of the thread it searched; the settings recorded on the run (toggles and Deliberation from the question's checkpoint, system prompt and summarizer from checkpoint metadata, where LangGraph copies string `configurable` values); each answer with its metrics; and the vote as it stood (`db.get_answer_vote`). A summary on the path is **kept**: the original answers were written from it (a small-context model jumps to it), so dropping it would compare new answers from the whole history with old ones from a summary; the replay's own compaction still decides whether to summarize again. `replay_case(case, models)` (default: the case's own, through `resolve_models`: unknown or keyless models are refused; so is a summarizer whose key is gone, never swapped) runs in a new thread `replay-…` titled "Replay: <title>", seeded with that history (`runs.seed_thread`, so the transcript there shows only the question and its answers; the seed is context), with the documents (searched files indexed into the new thread through an injectable `indexer`) and settings, through `arena.run_arena`; it never reads or writes the source thread. Each new answer is diffed (`textdiff.diff_texts`) against the case's answer from the same model, else the one voted best, else none (`baseline: null`). Times are ISO with `+00:00`. REST `POST /cases`, `GET /cases`, `GET /cases/{id}` (with replays, newest first), `DELETE /cases/{id}`, `POST /cases/{id}/replay` (not streamed, like `POST /chat`); CLI `cases save|list|show|delete`, `replay <case> -m …` (prints the models and asks unless `--yes`; `--diff`); MCP `save_case`, `list_cases`, `get_case`, `delete_case`, `replay_case`. Web: "Save as a case" under a finished multi-model turn's cards (saved by the reply on screen), "Saved cases" in the Sidebar (`SavedCasesDialog`, `useSavedCases`, `lib/cases`).
- **Peer review** (`services/review.py`): every model that wrote one of a set of answers scores the others from 1 to 10 with a reason, by letter (shuffled per set), never its own, each in its own seeded order; scores, not a ranking (two answers leave each reviewer one other). A failed reviewer is an error in the result, answers by one model are refused. Stored per set (`answer_reviews`, deleted with the thread), never fed into a synthesis. REST `POST /synthesis/reviews`, `GET /synthesis/reviews/{thread_id}`; CLI `review [--answers] [--list]`; MCP `review_answers`, `list_answer_reviews`. Web: "Have them score each other" under a turn's compare cards, `PeerReviewPanel` ("evidence to weigh, not a verdict"), `useAnswerReviews`.
- `services/history.py`: `thread_tree`, `compact_tree` (the CLI's JSON and MCP's tree: one entry per node with parent, role, model, kind, turn, time and the text as written), `path_at`, `search_thread` (hits point at the tree's node; refuses queries under two characters and unknown threads), `diff_answers` (two replies by checkpoint id through `textdiff.diff_texts`: rows `same | changed | only_a | only_b`, a changed one with word `segments`, per-group counts and `summary_text`; refuses an unknown thread or a checkpoint that isn't a reply; reads only, so it has no route and no `PARITY` entry), `delete_branch` (any checkpoint of a message counts as its node; refuses the thread's start).
- **Votes** (`services/votes.py`): a person's judgment of one turn's answers — the best one, a tie or all bad — with the kind of task (`TASK_TYPES`, chosen by the person; nothing classifies it, so every label is one they can stand behind) and an optional reason. One per turn in `answer_votes` (voting again replaces it; deleted with the thread, kept when a branch is deleted). Read blind, answers are lettered by `blind_order(turn_id, models)`: FNV-1a of `turn:model`, mirrored in `frontend/src/lib/blind.ts` (both test the same vectors), by model rather than checkpoint because the web UI letters cards while they stream. Win rates are pairwise: a best answer is a win over each other answer of its turn, a tie a tie for every pair, "all bad" counted apart and never as a loss; `win_rate = (wins + ties/2) / (wins + losses + ties)`. REST `POST /votes` (default: the latest turn; `best` by checkpoint or blind letter), `GET /votes`, `GET /votes/stats`, `DELETE /votes/{thread}/{turn}`; CLI `vote` (`--show` prints the answers blind, `--best/--tie/--all-bad`, `--delete`) and `votes` (`--task`, `--list`); MCP `vote_answers`, `list_votes`, `vote_stats`, `delete_vote`. A model's judgment is peer review (`services/review.py`), never a vote.
- `services/subtree.py`: notes a person writes on a tree node, in one table `node_notes` (keyed by thread and node checkpoint id; deleted with the branch by `delete_checkpoint_data` and with the thread): `label_node` (a branch name, at most 80 characters, and a bookmark), `summarize_subtree` (the node and everything below it, every branch labelled with the entry it replies to, written by `graph.default_summarizer()` or a named model: one helper call, stored on the node, **never written into the thread**, where `is_summary_message` and the compaction policy would take it for a history summary), `clear_subtree_summary`. Tree nodes carry `name`, `bookmarked`, `subtree_summary` ({text, model, nodes}) in their metadata (`tree.apply_node_notes`), so do `compact_tree` and the CLI's ASCII tree. REST `PATCH /history/{thread}/nodes/{node}`, `POST`/`DELETE .../summary`; CLI `node <cp> --name/--bookmark`, `summarize-branch <cp> [--model] [--clear]`; MCP `label_node`, `summarize_subtree`.
- **The answer diff has two copies of one contract**: `services/textdiff.py` (difflib; the CLI and MCP) and `frontend/src/lib/diff.ts` (an LCS; the web UI). Prose is cut into sentences after markdown formatting is stripped (headings, list items, quotes and table rows start their own), code blocks into lines, JSON pretty-printed with sorted keys first; a run only in A next to a run only in B is paired position by position when the words overlap (`PAIR_SIMILARITY`, punctuation not counted) and diffed word by word. Change both together; their tests use the same cases.
- `services/threads.py`: `list_threads`, `rename_thread`, `delete_thread`, which refuse a thread that doesn't exist or a debate lane (`{thread}::…`). `list_threads` never shows a raw thread id as a title: a thread nobody titled (from before auto-titling, or a debate's parent) gets the title auto-titling would have written, derived on every listing and never stored — `chat.thread_title` of its first message (`db.first_messages` reads only the first few checkpoints of each untitled thread, in id order), else "Debate: …" with its latest debate's question (stored `questions`, else the lanes' first message), else `UNTITLED` ("Untitled conversation"). Such rows carry `title_derived: true`; the sidebar sets them in italics and the CLI table too, and Rename stores a real title.
- Debates go through `services/debate.py` (`run_debate`, `continue_debate`, `synthesize_session`, `debate_transcript`, `session_view`), the same engine the WebSocket uses. Do not reintroduce separate orchestrators in `graph.py`.
- Diagnostics go through `logging` (`app.*` loggers, stderr): the server logs INFO (`main._configure_logging`), the CLI WARNING unless `--verbose`, MCP WARNING. Nothing in services prints; `stdout_to_stderr()` still guards CLI `--format json` and every MCP tool (the stdio transport **is** stdout) against third-party prints.
- `backend/.env` is read by the entry points only: `python -m app.main` (the reloader's worker inherits the environment), `python -m app.mcp_server`, the CLI. Importing an app module never loads it, so tests and `uvicorn app.main:server` see only their own environment.

**CLI — `app/cli.py`**
Typer CLI installed as `crucible`. Turns: `chat` (one model) and `arena`, both with `--from <checkpoint>` (branch; to edit a message, branch from the checkpoint before it), `--after-debate <session>`, `--deliberate` (Deliberation; prompt optional), `--attach <file>`, `--rag`, `-w`, `--summarizer`, `--system`; `--join-turn <turn id | reply checkpoint>` adds the models (`-m`, needs `--thread`) to an answered turn instead (no prompt, `--deliberate`, `--attach` or synthesis). `debate` (`deliberate` is a hidden alias: it was the command's first name; Deliberation itself is `--deliberate`) with `--from`; `debates list|show|continue|redirect|delete`; `synthesize` (`--thread` [`--answers <cp>`… `--from` `--mode merge|compare|checklist|ask` `--keep` `--question`] or `--debate`), `review` (peer review; `--list`); `cases save|list|show|delete` and `replay <case> [-m …] [--yes] [--diff]` (saved cases). Threads: `threads` (list, `--rename`, `--delete`), `tree` (each node's checkpoint id; `--format json` is `history.compact_tree`; `--open` uses `?thread=`, honoured by `useThreads`), `messages` (`--at`; summaries as a dim marker, a reply's recalled count under it), `context` (`--at`, `-m`: what the next turn would send each model), `node` (name or bookmark a node), `summarize-branch`, `vote`, `votes`, `search`, `diff <cp_a> <cp_b>` (what differs between two answers; `--unchanged` prints the shared sentences, `cli_display.render_diff` marks A's lines `−` and B's `+`, removed words struck and added ones underlined), `delete-branch`, `upload` (`--list`). `models`, `keys` (`--set` asks for the value without echoing; `--unset`). List options repeat the flag (`-m a -m b`). Each answer is followed by a dim metrics line (`cli_display.print_metrics`, `metrics.describe`) and a multi-model turn by its total; JSON answers carry `metrics`. `--format json` puts only the JSON document on stdout; errors exit 1 with the message on stderr, option combinations that can't work exit 2 before anything runs, and a failed model or synthesis exits 1. User and model text is printed escaped (Rich markup would swallow `[int]` and crash on `[/x]`): `print_error`/`print_success` escape, `print_info` call sites escape what they interpolate, tables use `Text` cells. `debates continue`/`redirect` take settings only to override the debate's stored ones (`--rag/--no-rag`, …). Ctrl-C stops a CLI debate (the run leaves it `interrupted`) and says how to resume: the CLI runs it in its own process, so cancelling the command is what stops it (unlike a closed browser tab).

**MCP server — `app/mcp_server.py`**
FastMCP tools returning dicts, one shape per thing: an answer is always `{model, model_name, content, checkpoint_id, error, metrics}`, debate rounds are always a list, every checkpoint id is the tree node's. Each description states what it returns **before** its `Args:` section: FastMCP turns `Args:` into parameter descriptions and drops the rest of the docstring. A `thread_id` must exist (omit it to start a thread); a new thread whose first turn failed entirely is removed. Tools: `list_models`; `invoke_arena` (one model and `synthesize=false` is a chat turn; `parent_checkpoint_id`, `after_debate_session_id`, `deliberation`, `attachments` as local paths, `use_rag`, `use_web_search`, `system_prompt`, `summarizer`, `join_turn`: add `models` to an answered turn), `synthesize_answers` (`mode`, `keep`, `question`), `list_answer_components`, `review_answers`, `list_answer_reviews`; `save_case`, `list_cases`, `get_case`, `delete_case`, `replay_case` (saved cases); `run_debate`, `continue_debate` (more rounds, `inject`), `redirect_debate`, `synthesize_debate`, `list_debates`, `get_debate` (the transcript, with `rounds_from` / `max_chars`), `delete_debate`; `list_threads`, `rename_thread`, `delete_thread`, `get_thread_tree` (checkpoint ids), `get_thread_messages` (summaries as role `system` / kind `summary`; replies carry `context`), `get_thread_context`, `label_node`, `summarize_subtree`, `vote_answers`, `list_votes`, `vote_stats`, `delete_vote`, `search_thread`, `diff_answers` (two replies' diff, `history.diff_answers`), `delete_branch`, `upload_document`, `get_branch_answers`, `get_thread_summary`, `get_thread_status`. Failures raise `ToolError` (never an `"Error: ..."` string). A debate call that is cancelled leaves its session `interrupted` (the run's own cleanup; every consumer closes the run with `aclosing`): the tool call is that run's only owner, unlike the web UI's debates, which the server's run registry keeps going.
- CLI and MCP are tested against the real graph with a fake LLM in `tests/test_cli_mcp.py`. Don't go back to mocking `open_graph`: the old mocked tests hid a crash in every command's cleanup.

**Debate system — `services/debate.py`, `services/peers.py`, `services/synthesis.py`, `services/convergence.py`, `api/debate.py`**
Multi-round structured debate between ≥2 models, positioned as an **argument explorer**. Debate doesn't reliably make models more correct — majority voting explains most of its gains, and models conform to majorities and to stronger or named peers — but it does show an outside judge, the user, the strongest arguments and where they conflict. For an answer to rely on, the UI points to Arena's independent answers + Synthesis. Key design points:
- Each model gets its own LangGraph sub-thread, scoped to the session: `{parent_thread_id}::{session_id}::{model_id}`; synthesis uses `{parent_thread_id}::{session_id}::synthesis`. Both are **stored** in the session row (`thread_ids[model]`, `thread_ids["synthesis"]`) and every reader uses what is stored: `db.synthesis_thread_id(session)` / `db.session_thread_ids(session)`. Sessions created before the scoping stored `{parent}::{model}` and have no synthesis key (derived as `{parent}::synthesis`); they still load, but share those threads with every other such debate on the parent. Unscoped ids made a second debate's round 0 see the first one's question, its tree walk the first one's rounds, and a delete erase both.
- **Rounds.** `DEFAULT_ROUNDS` (2) is the only default: MCP and the CLI fall back to it, and `GET /models` ships it as `limits.default_debate_rounds`, which seeds `useDebateDefaults` until the person saves their own. Kept low because later rounds pull models toward each other's answers (conformity) more than toward correct ones, and most of debate's gain over one answer is the majority of the independent first round (roadmap Phase 1). The dialog and the Control Panel warn above it (`roundsAdvice`); `MAX_ROUNDS` is a spend limit, not advice.
- Session limits (`check_session_config`, the one check behind REST, CLI and MCP; `ValueError` → 400 / exit 1 / `ToolError`): 1 to `MAX_ROUNDS` (10) rounds, at least two **distinct** participants, and participants, `synthesizer_model` and `llm_judge` all in `MODEL_REGISTRY`. The API has no authentication, so the round cap is what bounds one request's spend. `run_debate` also dedupes and caps stored sessions, and `_stream_round` counts its producers (it used to count finished model ids in a set, so a repeated model left the round waiting forever). A session runs `MAX_ROUNDS` in all, however many calls (start, continue, redirect) it takes (`_rounds_allowed`). The frontend reads the limit from `GET /models` `limits`.
- Starting from a checkpoint: `parent_checkpoint_id` is a checkpoint of the **parent** thread. `seed_from_parent` reads the parent's path there and seeds every empty sub-thread with its messages (`runs.seed_thread`, marked `crucible_seed` in checkpoint metadata); all rounds then run from the sub-thread head. It used to be passed as the sub-thread's `checkpoint_id`, where it doesn't exist, so the models saw only the debate prompt. Seeded messages are context, not debate: the lane walk, `format_messages` (the sub-thread history the restored transcript reads), `debate_rounds` and `_first_prompt` (both via `_debate_messages`) skip it: the tree and history skip every checkpoint no longer than the seed (the run-input checkpoint after the seed still ends on its last message).
- All models stream concurrently per round via `asyncio.Queue` in `_stream_round`
- Round 0 is each model's **independent answer** (the question alone). The transcript shows each participant's first and latest answer to the current question side by side right before the argument map (`PositionShiftPanel`, from the pure `positionShifts`; after a redirect, the new question's rounds), so what a participant said before seeing the others is next to where it ended; its "Show changes" toggle per participant replaces the two answers with their diff (`DiffView`, the same view as the compare cards' dialog). The transcript and the tree's round band say so ("Round 1 · independent answers" / "Round 1 · independent": `roundLabel()` in `lib/debateTranscript.ts`, also used by `DebateRoundBands`), so users can compare those answers with the post-debate rounds. A round 0 (or a redirect's first round) with fewer than two answers ends the debate there (completed, no argument map, an `error` saying why): there is nothing to debate. Each `debate_round_end` carries the early-stop check's `verdict` when one ran.
- **Questions.** The session stores the question each stretch of rounds answered (`questions: [{round, prompt}]`) and what the person injected (`injected: [{round, message}]`). A redirect (`run_debate` on a session with rounds) continues the round numbering under a new question, each lane keeping what it said; its first round is the question alone. The transcript, `debates show`, the argument map and the record a chat turn reads (`continue_from_debate`, rewritten once the debate has changed: `crucible_debate_version`) all say which rounds answered which question. Sessions from before have their first question recovered from the lanes.
- Rounds ≥1 ask a model to say where its position changed and to change it only for an argument or evidence it had not weighed (in the cross-examination prompt, and for named peers also in the deliberation system prompt); they used to tell it not to contradict itself, which held wrong answers as firmly as right ones.
- **How peers are presented is a strategy** (`services/peers.py`, selected by name from `PEER_PRESENTATIONS`). `AnonymousPeers` (the default) labels participants "Participant A/B/C…" — fixed for the session from its id, so "Participant B is wrong" in round 1 still means B in round 2 — and reshuffles the listing order every round with a `{session_id}:{round}` seed, so prompts are reproducible; it tells each model its own label and never a model name. `NamedPeers` reproduces the original prompt (model ids, "You are {model_id}."). The cross-examination prompt, the judge prompt (`JudgeCheck(model, peers, …)`) and the synthesis input all label through the same instance (`session_peers(session)`). Anonymous rounds also skip the graph's deliberation mode (`names_in_history = False`), because it tags every earlier turn with its model id and its critic role tells the model its own id: those rounds get only the person's system prompt, and the cross-examination prompt carries the critique instructions. The choice is the session's `peer_labels` column (validated by `check_session_config`; `CreateSessionRequest.peer_labels`, CLI `--peers`, MCP `peer_labels`, and in the web UI the debate dialog's "Participants" select, defaulted from the Control Panel's "Anonymous Participants" toggle in `DebateDefaults.peer_labels`). A session stored before the column existed has `NULL` and is treated as **named** (`STORED_PEER_LABELS`): its earlier rounds already named each other, so anonymizing a redirect or its synthesis would hide nothing and misdescribe what ran. The UI keeps real display names; each lane carries `peer_label` (`peer_legend()`), shown in its header and in the debate banner's legend (`peerLegend`) so replies and the argument map that say "Participant A" can be decoded.
- **How participants are told to argue is a strategy too** (`services/stances.py`, the session's `stance` column: `{mode, sides, advocate}`, NULL = open; `check_stance` inside `check_session_config`). `OpenStance` is the original debate. `AssignedSides`: each argues the side it is given, whatever it thinks — the setup in which debate measurably helps the person judging (Khan et al. 2024, Kenton et al. 2024); round 0 is each one's opening case (`roundLabel(0, …, "sides")` reads "opening cases"), and the sides are shown to the others beside the labels (`public_note`). `DevilsAdvocate`: round 0 is everyone's own answer, the advocate's included; from round 1 the advocate argues against what the others hold in common, and the others are not told which participant it is (they would discount it). The stance owns the first-round brief and the later rounds' closing instruction, which it **replaces** (the open "State your position now…" would contradict "don't switch sides"). Both assigned stances refuse an agreement judge (nobody is meant to agree; stability still works). The argument map has a framing per stance (`ASSIGNED_SIDES_MAP`, `ADVOCATE_MAP`), and the synthesizer, the record a chat turn reads (`debate_record_text`), `session_view` (`stance`, `stance_notes`), the tree's lanes (`stance_note`) and `session_metadata.stance`, and the `debate_round_start` event all say who was told to argue what. A redirect keeps the stance. Named "stance", not "roles": `role_warnings` already means a judge or synthesizer that is also debating. REST `stance` on `POST /debate/sessions`; CLI `debate --side … --side …` (given in turn) or `--advocate <model>`; MCP `run_debate(sides=, advocate=)`; web: the dialog's "How they argue" (`StanceSettings`, `lib/stances`).
- **Debate synthesis is an argument map, not a verdict.** `synthesis.py` has one prompt shape and takes a `SynthesisFraming` (description + instruction) from the caller: Arena passes `INDEPENDENT` (unchanged — merge independent answers into one), debates pass `ARGUMENT_MAP` with every round of every participant (`debate_rounds()`, read from the sub-threads; a failed round stays an empty slot so later rounds don't shift). It asks for the distinct positions, each one's strongest arguments and evidence, who changed position and the argument that changed it (or that none did), and what remains unresolved and what would settle it; it never declares a winner or a consensus and says agreement reached by debating is not evidence by itself. Don't branch on the mode inside `build_synthesis_prompt`; add a framing.
- Cross-examination (round ≥1): each model receives all peers' previous responses as a single HumanMessage (not raw AIMessages — this is intentional to avoid `sanitize_messages` breaking alternating-turn invariants)
- Early stop has two meanings that must not be conflated. **Stability** (`StabilityCheck`): each model's answer is compared with *its own* previous answer (embedding cosine via `run_in_executor`, reuses `rag.get_embeddings()`); two models holding opposite positions are perfectly stable. **Agreement** (`JudgeCheck`): an LLM judge reads all current answers once per participant, the order rotated so every answer takes every position once (reversing alone would leave a middle answer in the middle), and agreement counts only when every reading finds it (LLM judges have a systematic position bias; a verdict that changes with the order is reported as not counting); it is the only check that may be called consensus or "converged". Stability always requires every model; `mode: "any"|"all"` only says how the two checks combine when both are set (it used to also let one stable model stop the whole debate, while the UI described it as combining conditions). The UI shows a stability stop as "answers stopped changing" (status `stable`) and only a judge stop as "models now agree (after debating)" (`converged`), via `earlyStopStatus(method)`; `CombinedCheck` reports the method of the check that actually stopped the debate. The policy key `convergence_threshold`, the `convergence_score` / `debate_converged` frames and `round_scores` keep their names because stored sessions and clients use them; all three carry stability.
- `api/debate.py`: `DebateConnection` is one client socket on one session; it hands the debate to the run registry (`services/live.py`), which owns the task, and watches the session. Client frames dispatch through its `COMMANDS` table (`debate_start`, `debate_redirect`, `debate_inject`, `debate_control`, `debate_synthesize`); every socket on the session gets the run's frames.
- Convergence (`services/convergence.py`) is a strategy: `build_convergence_check(policy, peers)` returns `StabilityCheck` (embedding cosine against each model's own previous answer, `embed` injectable), `JudgeCheck` (LLM judge, factory injectable), a `CombinedCheck(mode)` of both, or `None`. `run_debate` only calls `check.evaluate(previous, current) -> Verdict`.
- REST: `POST /debate/sessions`, `GET /debate/sessions` and `GET /debate/sessions/{id}` (rows add `question`, `questions` and an ISO `created_at`), `GET /debate/sessions/{id}/tree` (`debate.debate_tree`), `GET /debate/sessions/{id}/transcript` (`debate.debate_transcript`: rounds aligned by number, each with its question, responses and errors), `DELETE /debate/sessions/{id}`
- WebSocket: `WS /debate/ws/{session_id}` — handles `debate_start` (`documents` or `document_names`), `debate_inject`, `debate_redirect`, `debate_continue` (`rounds`, optional `message`: more rounds of a stopped debate, e.g. one interrupted by a server restart), `debate_control` (`stop`/`pause`/`resume`), `debate_synthesize`. A run that fails reaches every socket on the session as an `error`. A socket that connects while the debate runs gets `debate_resume`, then `attached` (see the run registry above); one with no first frame only attaches.
- Live controls are the run's `DebateControl` (kept on its `DebateRunState`, not on a connection), so pause, resume and inject from any socket on the session — a reattached tab, a second one — reach the same run: pause takes effect **between rounds** (the handler reports `pausing` to every socket, `run_debate` reports `paused` then `running`), and injected messages are appended to the next round's prompts; one that arrives after the final round is reported as an `error`, not dropped. Synthesize and redirect cancel a running debate first. A debate outlives its socket: a disconnect stops nothing, and a restored `running` or `paused` session is attached to, not shown as interrupted.
- **The run owns the session's status.** A session starts `pending`; `run_debate`, `continue_debate` and `synthesize_session` claim it with one conditional UPDATE (`db.claim_debate_session`: refused while another client — socket, CLI, MCP — runs it, unless `force`, for one left marked running by a backend that died) and settle it on the way out (`_claimed`): completed, `interrupted` if rounds started and didn't finish, or back to the earlier status if nothing ran (a refused start). Transports don't write statuses (except `completed` after a stop). `interrupted` now means the process running the debate stopped it — a server shutdown or restart, a cancelled CLI or MCP call, an error — never a closed tab. Server startup marks sessions still `running` or `paused` interrupted (`db.interrupt_running_debates`, in `main.lifespan` only: the CLI runs `init_db` while a server may be mid-debate), since none can outlive the process that ran it, and server shutdown cancels its runs (`LiveRuns.close`), which settle as interrupted. Continue, redirect and synthesis reuse the start's settings (`settings`: system prompt, summarizer, toggles) unless the call names others. Clients without a live connection (CLI, MCP) control a debate in steps instead: `continue_debate(session, rounds, inject)` runs more rounds of a stopped debate, reading the previous round, the question and the attached documents from the sub-threads (so pause = run fewer rounds, resume/inject = continue), and `run_debate` on an existing session is a redirect.
- `MODEL_TIMEOUT_SECONDS` bounds each model's whole graph run per round, but a reply whose `draft` node already finished is kept if later nodes run long. Neither stability nor the judge is satisfied while any participant failed that round: `JudgeCheck` returns not-converged without calling the judge, which would otherwise read only the surviving answers and could call that agreement.
- `database.py` stores debate sessions in a `debate_sessions` table; `tree.py` has `build_debate_tree` which computes deterministic lane layout (no dagre): `x = lane_index × 300`, `y = round_num × 160`
- Debate lanes render **AI responses only**. Each round also writes a human checkpoint (the generated cross-examination prompt); rendering those duplicated the question in every lane and made `round_num` count checkpoint depth instead of debate rounds. The original question is emitted once as a shared `debate::prompt` node above all lanes, with edges fanning out to each lane's round 0. A node's `round_num` is the debate round: the lane walk counts round prompts, as `debate_rounds` does, so a reply after a round the model failed keeps its round (counting replies put it a round early, unlike the transcript). Node ids are `{model}::{checkpoint}` with the checkpoint `stream_end` reports, and the synthesis node names its author (`active_peer` / `model_name` are the synthesizer).
- The synthesizer is `db.session_synthesizer(session)`: the stored `synthesizer_model`, else the first participant (sessions stored before the default below; auto-synthesis used to be skipped when none was named). `create_session` resolves a session that names none with `debate.default_synthesizer(participants)` and stores it: the first of `REFEREE_MODELS` (registry; kept apart from `DEFAULT_ARENA_MODELS` because a referee must come from one more family than the default debate has) from a family that isn't debating and has a key, else the first participant (the dialog's "Automatic"; the CLI's `--judge` default goes through it too). Models favour text they recognise as their own. `debate.role_warnings(session)` names a synthesizer or agreement judge that is also debating; it reaches REST (create and session rows), MCP (`run_debate`, the session view), CLI `debate` (stderr, and `warnings` in JSON) and the web UI (a toast on start, the banner on every reopen; the dialog warns before, `debatingRoleWarning`). A manual synthesis stores the model it used. The `synthesis::pending` placeholder is drawn only while a synthesis is coming: `auto_synthesize`, and status `running` or `paused`. A manual synthesis draws its real node once written.
- `LANE_WIDTH` / `ROUND_HEIGHT` are mirrored in `frontend/src/hooks/useDebateTree.ts` (which the canvas overlays import) so optimistic pending nodes land exactly where the real node will appear. Change both together.

### Frontend (`frontend/src/`)

**App shell — `app/page.tsx`**
Composition only: calls the hooks below, keeps the few pieces of UI state that belong to no hook (composer input, documents, toggles, error modals) and lays out Sidebar | AppHeader + TreeCanvas/ChatView | ControlPanel. `useLayoutPanels` decides the side panels' layout: below the md breakpoint both are overlay drawers (closed by default, opened from the header's "Open sessions" / "Open settings"); wider, both dock and each collapses to a rail (persisted). New behaviour goes into a hook or component, not back into the page — it was a 1,500-line component before the split.

**Custom hooks**
- `useChatWebSocket.ts`: manages the WebSocket connection per thread, dispatches parallel model requests (one per selected model), buffers streaming tokens via `requestAnimationFrame` for smooth rendering, and handles `stream_start` / `stream_token` / `stream_end` / `title_update` / `error` messages. A model's error becomes a `ModelError` (shown inline by `ModelErrorBubble` with Retry, which resends that model's frame from its pinned parent); only errors with no model open a modal. `synthesizeBranches` sends a `type: "synthesis"` frame naming the sibling replies (`answer_checkpoint_ids`) for the chosen synthesizer with `parent_checkpoint_id: null`; the backend writes the prompt and hangs it from the question the answers responded to (turn-mates sit on different branches, so there is no common parent to name). When every model of a turn has finished it calls `onTurnSettled` (the page resets the branch point to Latest and reloads) — it must **not** make a reply the branch point: pinning the first `stream_end` checkpoint sent every model's next turn after that one model. Runs belong to the backend, so a dropped socket marks nothing: the hook reconnects with backoff (`lib/transport.reconnectDelay`, not on a thread switch, where its own close is expected) and catches each reply up from `stream_resume`. A reply is marked `stopped` (`lib/messages.markStopped`; the bubble says it is incomplete) only on Stop, on `stream_stopped` (another tab's Stop), or when the reconnected socket's `attached` names no live run for it — then the turn settles and the thread reloads, showing whatever was written. A run this tab didn't send (after a reload, or from another tab) is adopted from its `stream_resume` / `stream_start`: its question (`lib/messages.withResumedQuestion`, kept through history loads by `reconcileMessages` until the path holds the turn: `GET /history` ends at the last answered turn) and its reply as a bubble or, for several models, cards (`lib/turns.adoptLiveReply`), counted toward settling like a turn sent here. Stop pressed while the socket is down goes out when it reconnects. A turn sent to several models streams into `liveTurn` (`lib/turns`: one reply per model, in the order asked — content, streaming, stopped, error, its node id once `stream_end` gives it), not into `messages`; a single-model turn and a synthesis stream as bubbles. A failed model's reply carries its error (Retry streams it back into the same card), and Stop marks what is still streaming as stopped. It keeps each streamed reply's full text (`replyTexts`, by tree node id). It refreshes the thread list (`onThreadsChanged`) when a turn finishes and on `title_update` (and leaves the tree alone then). `addModelToTurn(reply, turnId, model)` ("Add a model") sends one `join_turn` frame naming the turn by its reply on screen and streams into that turn's grid (`lib/turns.startJoin`: `joins`, keyed `turn-<turnId>` like the settled grid, so nothing remounts; a lone reply becomes a two-card grid). A finished join calls `onTurnJoined`, not `onTurnSettled`: the page only reloads the path on screen, because nothing new was asked and the branch point and who answers next must not move. An adopted run with `joins_turn` is a card of its turn and adds no question.
- `useHistoryTree.ts`: fetches the tree from `GET /history/{thread_id}` (optional `?checkpoint_id=`) and keeps three checkpoints apart: `chosen` (the node the person picked to continue from — click, Branch from here, Edit & fork — or **null for "the latest turn"**; it is the next frame's `parent_checkpoint_id`, and only an explicit action sets it), `head` (the answered head a fetch without a checkpoint reports) and `shown` (the path on screen). With `parent_checkpoint_id: null` the backend continues every model from its own reply in the latest turn, so Send after a three-model turn is three parallel conversations. Only the newest request's response is applied (a request counter), another thread resets all three (the previous thread's checkpoint used to leak into the next send), a reload of the same thread keeps the tree on screen, and failures reach a toast. The Tree/Arena view is persisted (`crucible_view`, default Arena), so a restored session and a new one open the same view. Messages are merged by `lib/messages.reconcileMessages` (keyed by `checkpoint_id`, position only for older payloads).
- `useThreads.ts`: manages thread list CRUD, and which thread opens on load (`?thread=`, else the stored one). The stored thread's history request goes out from the mount effect alongside `GET /threads`, not after it; `resolved` stays false until the thread to reopen is known, and the page renders neither the landing view nor a tree until then (a restored session used to open on the landing view and wait out its 0.4 s exit animation before the tree could mount).
- `useDebateTree.ts`: manages debate tree state; fetches from `GET /debate/sessions/{id}/tree`; handles optimistic pending nodes during streaming rounds. A reply's `stream_end` settles its placeholder into the server's node (`settlePendingNode`: same id, the backend's excerpts), so it reads and selects at once and the refetch replaces it without a remount. Reading a node in full: its Read button (`onReadNode`) opens `DebateReplyDialog` with the transcript's reply (`lib/debateTranscript.debateReplyFor`: by the node's checkpoint, else model and round; the synthesis node is the latest synthesis).
- `useDebateSession.ts`: everything about the debate on screen — active session (persisted), transcript, status, the debate WebSocket, and the actions (start, inject, redirect, pause/resume, continue, synthesize, close, delete, switch). Wraps `useDebateTree` and `useDebateSessions` (the sidebar's list, refreshed on mount, on another thread and when a debate is created, finishes or is deleted — not on every thread-list change). A restored debate that isn't running is read in one request from `GET /debate/sessions/{id}/transcript` (`lib/debateTranscript.transcriptMessages`, rounds aligned by number, a failed model's slot showing why); its question (`session.question`) is what a later synthesis or redirect is about. A restored `running` or `paused` one (`mayBeLive`) is attached to: a socket with no first frame; on `debate_resume` the hook holds the live frames, reads the transcript up to the round in progress (`resumedMessages`), lays that round over it (the reducer's `resume` action: stored answers kept, the rest as the backend has them, streaming ones still open), re-adds their pending tree nodes and then applies the held frames; `attached {live: false}` (it finished meanwhile, or the server restarted) shows it as stored. A dropped socket reattaches the same way, with backoff, instead of calling the debate interrupted. `continueDebate` sends `debate_continue` (Resume on a debate a server restart interrupted: the rounds it has left; one more round on a finished one); a refusal (another client runs it) restores the previous status. Leaving a debate — a sidebar switch, a new debate, another thread, New Session, home, a reload — asks nothing, because it stops nothing: the debate runs on and the sidebar row shows it running. Closing it (the banner's X) stops it, so that asks first (`closeWarning`), and so does Redirect. The tree is refetched once per burst of `stream_end`s (`useDebateTree.refreshSoon`); the 3-second poll and the post-synthesis status poll are gone, the socket's events drive it. A debate-only thread's latest debate opens once per visit (closing it used to reopen it).
- `lib/debateTranscript.ts`: **pure** `transcriptReducer` turning debate events into chat bubbles, plus `debateControls(status)` (which buttons exist in which state) and `restoredDebateStatus`. Unit-tested; put event→bubble logic here, not in the hook.
- `useTreeActions.ts`: checkpoint actions for the conversation tree (select, view, delete, edit-and-rebranch, branch-from, drag, tidy layout) and the composer's branch point (`lib/branching`: `isLatest` means nothing is chosen). `viewCheckpoint` shows a path read-only (the compare cards' "Read in full"): reading another model's answer must not change what the next message continues or who answers it. `editAndRebranch` fetches the message's path and puts its full text in the composer (the tree label is a 40-character, markdown-stripped preview). Clicking a node tells `useReplyTarget` who answers next — only on an explicit click; the post-turn history refresh must never change who answers (it used to collapse a multi-model selection to one).
- `useReplyTarget.ts`: who answers the next message (`lib/replyTarget`). A clicked model's reply is continued with that model alone, or with every selected model through the branch chip's switch, for as long as the branch point is that model's reply (the click, then each reply it writes); any other node, a branch point that moves to another model's reply ("Latest", or the newest reply after every model answered), a new debate or another thread goes back to the Control Panel's selection. It never changes the selection: clicking a reply used to overwrite it, and once the selection was persisted one click left a three-model arena as one model on every later visit. Send, Deliberate and the header use who answers; a debate's participants and the synthesis default use the selection.
- `useDocuments.ts`: the files attached to the next message. An upload (`POST /upload`) stores the file on the thread; frames send only `document_names` (also `debate_start`), never the text once per model. Attachments belong to one turn (the composer says so) and one thread (opening another drops them); the file input is reset after each pick so the same file can be attached again; the upload shows as a pending chip and a failure toasts the backend's reason. "Search my documents" (`use_rag`) defaults off and stays the person's choice: after an upload the page only says it reaches the file in later turns. Turning it on by itself searched the file in the same turn its whole text was already attached to (twice in context), and the first search loads the embedding model, holding that turn for seconds.
- `useSystemPrompt.ts`: the persisted system prompt (empty by default). Requests carry it only while it is not blank; its length limit comes from `GET /models` (`limits.max_system_prompt_chars`).
- `useVotes.ts`: the open thread's votes by turn, voting (the stored vote replaces the turn's, `version` bumps so `useVoteStats` reloads the Control Panel's win rates), and two preferences: blind comparison (`crucible_blind`, off by default) and the last task type chosen. Memoised.
- `useTreeView.ts`: how the tree is folded — collapsed nodes (persisted per thread, `crucible_collapsed:<thread>`) and the hoisted subtree (shown alone; forgotten on another thread); `revealNode` opens whatever hides a node (a bookmark jump). What is drawn is `lib/treeView.visibleTree`.
- `useNodeNotes.ts`: rename, bookmark, compress into a summary (then the branch folds under it) and remove a summary, each reloading the tree; its return value is memoised, because the canvas rebuilds its nodes whenever it changes.
- `useNextTurnContext.ts`: what the next message would send whoever answers it (`GET /history/{thread}/context` for `chosen`, else the head, and `reply.responders`), refetched when any of those or the head moves; null while loading or after a failure, so the chip never shows stale numbers.
- `useSummarizerChoice.ts`: the persisted summarizer choice ("" = automatic). Requests carry it only while that model's family has a key, so a removed key falls back to the backend default instead of failing every summary.
- Small single-purpose hooks: `useAnswerDiff` (the compare cards' "Compare with…": both whole texts for `AnswerDiffDialog`, read without touching the history tree), `useToasts` (`pushToast(message, kind, title?)`; `kind` is `error | success | info` and required, so a confirmation never shows as a failure), `useConfirm` (promise-based, rendered by `ConfirmDialog`; questions only, with the action's verb as `confirmLabel`: information goes in a toast), `useBackendStatus` (header connection line), `useModelCatalog` (GET /models + the arena selection + `modelLabel` + `modelColor` + `availableModelIds` + `limits`: the backend's `max_system_prompt_chars`, `max_debate_rounds` and `max_prompt_chars`, which the system prompt field, the round inputs and the composer's counter use; `lib/catalog.FALLBACK_LIMITS` only until it loads, so there is no frontend copy to keep in step), `useDebateDefaults` (persisted Control Panel defaults), `useLayoutPanels` (see App shell), `useSavedCases` (saving a turn as a case, and the Saved cases dialog's list, open case and replay; returns one memoised object)
- REST failures: every `lib/api.ts` call goes through `ensureOk` (`lib/errors.ts`), which throws an `ApiError` carrying the backend's `detail`; callers show `errorMessage(e, fallback)` in an error toast instead of only logging it.
- Pure helpers in `lib/` (unit-tested): `composer` (which composer actions are enabled and the tooltip saying why not, the prompt limit included), `messages` (reconcile a loaded path, Edit & fork's text, stopped replies), `arenaCompare` (turn siblings for the compare cards), `turns` (live turns and the transcript's bubbles-and-grids layout), `catalog` (limits, catalogue colour, a family's `env_key`), `colors`, `errors`, `branching`, `replyTarget` (who answers the next message), `treeFit` (auto-fit fits the whole tree when it is readable, else the active node), `context` (a reply's context note, the branch chip's inherit line and per-model tooltip), `treeView` (folded and hoisted trees, arrow-key neighbours, what a bookmark jump opens), `spanBranch` (which reply a text selection is in, and its quote), `blind` (the blind order and `maskCards`), `debateTranscript`, `diff` (what differs between two answers: `diffAnswers`, `diffSummaryText`; the backend's `textdiff.py` contract), `cases` (saved cases' shapes, which models a case can be replayed on, what a replayed answer is compared with).

**Branching / Arena flow**
Multi-model Arena: `useChatWebSocket` sends one WS message per selected model simultaneously. Branching: `chosen` (a tree node id) is passed as `parent_checkpoint_id`; null (the composer chip's "Continuing the latest turn") lets the backend continue each model from its own reply in the latest turn. The compare cards group replies by `metadata.turn_id` (`lib/arenaCompare.turnSiblings`; same parent for threads without turns), since turn-mates now sit on different branches.

**Debate flow**
User selects ≥2 models → types prompt → clicks Swords button in ChatInput → `DebateConfigDialog` opens → on Start: `POST /debate/sessions` creates session, WS connects to `/debate/ws/{session_id}`, `debate_start` frame is sent. `useDebateSession` owns the debate WS lifecycle: the transcript (tokens RAF-batched per model, applied through `transcriptReducer`), round/status/stability state, and `useDebateTree` for the tree canvas. TreeCanvas switches to debate mode when there is an active session.

## Key Conventions

- All model IDs must be registered in `MODEL_REGISTRY` in `backend/app/registry.py` before use.
- The `langchain_anthropic` monkeypatch in `app/patches.py` is intentional — web-search beta events carry a plain-dict `container` that the chunk parser calls `model_dump()` on (found in 1.3.2, still present in 1.7.6, where the parser became the `ChatAnthropic._make_message_chunk_from_anthropic_event` method the patch now wraps; `tests/test_upstream_hooks.py` also runs a dict container through it). It and `GoogleProvider`'s override hook *private* upstream symbols, so `tests/test_upstream_hooks.py` asserts they exist and are still on the request/streaming path, and `patches.py` raises if its target is gone (it used to swallow every exception). `pyproject.toml` caps both packages below their next major (`langchain-anthropic<2`, `langchain-google-genai<5`); lift a cap only with those tests green.
- Backend uses `uv` for package management; never use `pip` directly.
- **Dependencies.** Declare every package the code imports (`langchain_text_splitters`, `httpx`, `numpy` and `starlette` once arrived only transitively) and nothing it doesn't (`unstructured`, `langchain`, `langchain-community`, `sqlalchemy` and `mcp` were declared but unused, and pulled most of the known vulnerabilities in). Upgrade with a cooldown so a freshly published, possibly compromised release isn't installed: `uv lock --upgrade --exclude-newer <date a week ago>`, `npm install … --before=<date>`; a fix newer than the cooldown waits for the next sweep unless its vulnerability is reachable here. Audit with `npm audit --omit=dev` and `uvx pip-audit -r <(uv export --frozen --no-hashes --no-dev)`, and weigh each finding by whether this single-user, localhost app can reach it: through the user's browser (cross-site requests, now guarded in `api/security.py`), through content it renders or parses (model output in markdown/KaTeX, uploaded PDFs via PyMuPDF), through installs (supply chain) or model files (embeddings from Hugging Face). Server-side DoS bugs matter only once it is exposed beyond localhost.
- Commits follow Conventional Commits: `feat:`, `fix:`, `docs:`, `refactor:`, `test:`.

## Dependency injection & testing

- **Isolation (`tests/conftest.py`):** every test runs with the provider keys cleared (a test that forgets a fake model fails for want of a key instead of making a paid call; tests that need keys set placeholders) and its own `Storage` (`conftest.isolated_storage`, also put on the app); `tests.storage_helpers.point(monkeypatch, db_path=…)` moves one location for the rest of a test.
- **Models:** never construct clients or patch module globals. Inject a factory: `config={"configurable": {"model_factory": CallableModelFactory(fn)}}` for a node, `with use_model_factory(...)` for anything that runs a whole graph, `ProviderModelFactory(providers=..., env=...)` to test provider selection.
- **Graph in routes:** put a graph or mock on `client.app.state.graph_app`; routes read it through `get_graph_app`. Without the lifespan it is absent and routes answer 503.
- **Browser guards:** a multipart/form/text POST through `TestClient` needs `headers={"X-Crucible-Client": "1"}`; `json=` posts don't. Test a guard on its own app: `create_app(origin_policy=OriginPolicy(...), allowed_hosts=[...])` (`tests/test_security.py`).
- **Debates:** every debate REST route is tested over HTTP in `tests/test_debate_routes.py` (create, list, get, tree, transcript, delete, the 404s, and what a delete keeps), against debates run through the debate socket with the app's lifespan graph and a fake LLM; reuse its `client` fixture and `_debate` helper for a route that needs a finished debate. The socket's controls are in `tests/test_debate_ws.py` (with a reattached socket's pause, inject and stop), runs that outlive their socket — a chat turn and a debate through a reload, a second socket, a stop from another socket, server shutdown — in `tests/test_live_runs.py`, request validation in `tests/test_debate_limits.py`, sub-thread scoping and seeding against the real graph in `tests/test_debate_threads.py`, the whole lifecycle in the browser in `e2e/tests/live.spec.ts`.
- **Convergence:** `SimilarityCheck(threshold, mode, embed=...)` and `JudgeCheck(model, factory)` take their dependencies; tests never load the embedding model.
- **React Flow in jsdom:** call `installReactFlowDom()` (`src/test/reactFlowDom.ts`): it stubs `ResizeObserver`, `DOMMatrixReadOnly` and element sizes, and nodes count as measured only after `act(() => measureNodes())`, so a test decides when auto-fit's signal arrives.
- **Frontend sockets:** hooks open sockets via `useSocketFactory()` (`lib/transport.tsx`); tests wrap the hook in `<TransportProvider value={factory}>` with a fake socket (see `useDebateSession.test.tsx`).
- **Pure first:** event→state logic belongs in pure functions (`lib/debateTranscript.ts`, `services/chat.build_turn_input`) with unit tests; hooks and connections only wire effects.

## Known Gaps

### Frontend visualization invariants (don't regress these)

These were bugs; the fixes are load-bearing.

- **TreeCanvas node sync** (`TreeCanvas.tsx`): the sync effect must apply restyles, not only structural changes. Theme swaps and label updates produce a new `processedNodes` with an identical ID set; skipping them left the tree painted in the old theme. `CustomTreeNode`'s memo comparator must therefore include `data.styling` and `data.metadata`.
- **fitView gating**: `fitView` reads React Flow's own store, so it is a silent no-op until the store holds *and has measured* the current node set. Gate on `storeNodeCount === externalNodes.length && storeNodesMeasured` (from the `useStore` selector). `useNodesInitialized()` does **not** flip true for these nodes — do not use it. Fit once per structural change, keyed on the node ID set. Fit the whole tree when `lib/treeFit` says it is readable (zoom ≥ `LOD_THRESHOLD`), otherwise the active node: fitting only the newest node parked the root above the canvas, under the header.
- **dagre**: build a fresh `dagre.graphlib.Graph()` per layout call. A module-level singleton accumulates every node from every thread and dagre spreads disconnected components side by side.
- **Arrow-key moves keep the zoom they started with** (`TreeCanvas` `keyMoveZoom`): React Flow's animated `setCenter` zooms out mid-pan, and a key pressed during that animation used to read the dipped zoom and keep it, so quick Home, ArrowDown on a slow machine left the tree in chips. A move that starts while an earlier one is animating reuses that one's zoom.
- **`@keyframes pulse`** lives in TreeCanvas's `<style jsx global>`. An MUI `sx` definition generates a scoped emotion name and will not resolve for pending nodes.
- **Model colours**: `FAMILY_META` in `registry.py` is the source of truth; the backend ships each family's `color` (and `env_key`) in `GET /models` and the resolved colour as `metadata.model_color` on nodes and `model_color` on messages and stream frames. `frontend/src/lib/colors.ts` has the one palette (`modelPalette`: text darkened or lightened until it reaches 4.5:1 on the theme's surface, a unit test checks every family) and the pre-fetch fallback (`modelFamilyColor`). `MessageBubble`, the compare cards, the tree, the minimap, the header and the Control Panel all draw from it; don't add another.
- **Absolutely-positioned overlay rows need an explicit `height`** (`DebateLaneHeaders`, `DebateRoundBands`) — otherwise the row collapses to zero height and `overflow` clips every child away.
- **Level of detail** (`CustomTreeNode.tsx`): below `LOD_THRESHOLD` (0.6) a node renders as a chip — colour bar, model name, word count — because a 40-char preview at 12px is unreadable once auto-fit drops the canvas to ~0.35. The chip is counter-scaled to stay legible, and that boost **must** stay capped (`LOD_MAX_BOOST` 1.35 against `LOD_CHIP_WIDTH` 190) or chips overlap the next column: the tightest layout pitch is `NODE_SPACING_X` 260. This applies to the selected node too — exempting it made the node you care about the least readable at that scale; its active styling still marks it.
- **Never print a raw model ID in UI a person reads.** The backend ships `metadata.model_name` on every node and `label` on every debate lane, from `display_name()` in `registry.py` (which also names a provider's dated snapshot, "gpt-5.2-2025-12-11", as its model: `catalog/names.py`, shared with `PriceBook`); `lib/modelNames.ts` covers frontend-created optimistic nodes. The exact ID belongs in a `title` tooltip.
- **The view never switches itself.** `handleSendMessage` / `handleDeliberate` (page.tsx) deliberately do not call `setShowTree`; sending used to yank you out of the tree. The exceptions: `editAndRebranch` and `branchFrom` ("Branch from here", useTreeActions), where moving to the composer is the point, and opening a debate, which shows its tree. The view is persisted, and New Session doesn't change it either; the empty tree says to switch to Arena to write the first message, and while models answer the tree shows a "Models answering…" status.
- **Canvas assertions must wait for idle.** Auto-fit animates the viewport for 500ms and Playwright refuses to click a moving element; use `waitForCanvasIdle()`. Auto-fit on the debate fixture also lands within rounding distance of `LOD_THRESHOLD`, so anything asserting on node *text* must call `ensureDetailZoom()` first or it will flip on layout noise.
- **Utility labels say what they do.** The themed vocabulary ("Quantum Nexus Online", "Council", "Deep Knowledge Search") was replaced with plain labels and a real connection/key status. "The Crucible", "Arena", "Deliberation" and "Synthesis" are kept — they name real mechanics.
- **Persisted debate session** (`crucible_active_debate`): only restore it once a thread is open and only if `parent_thread_id` matches, or a stale session hijacks the tree view of an unrelated thread. `listDebateSessions` returns **newest-first** — index 0, not `length - 1` (`db.list_debate_sessions` breaks one-second `created_at` ties by `rowid`; they used to come back oldest first).
- **Debate socket lifecycle** (`useDebateSession`): anything that puts a different debate on screen (sidebar switch, new start, thread switch) calls `closeSocket()` first, which detaches and closes the old socket (and cancels a pending reattach); otherwise the old stream keeps appending bubbles and its refetches overwrite the new tree. Closing a socket only stops this tab watching: the debate runs on the backend, and the next socket to attach catches up from `debate_resume`. A resume's held frames are applied only after the transcript load lands, or a frame that arrived meanwhile is lost or doubled. A socket's `onclose` only clears `wsRef` if it is still the current socket, and `onmessage` calls the *latest* handler through a ref. Code that loads a session itself sets `restoredRef.current` so the restore effect does not replace a live stream with a server snapshot. `useDebateTree` drops responses for any session other than the last one fetched, and `resolvePendingNode` removes one round's placeholder by id, not every placeholder for the model.
- **Debate model errors** arrive as `{type:"error", model, round}` with no `stream_end`; `transcriptReducer` closes that bubble and the hook resolves its pending node.
- **The persisted-debate write skips its mount run.** During hydration the active session is still null; writing it erased the stored session before it could be adopted.
- **Accessibility floor.** A global `:focus-visible` ring lives in `globals.css` (MUI resets outlines); icon-only buttons need an `aria-label`; sidebar rows are `<button>`s with their actions as siblings, never nested; no label below 11px (`e2e/tests/shell.spec.ts` checks all four). Beyond that: every Switch and Select has an accessible name (`ToggleRow` labels its Switch with its own label); toggle rows say their state with `aria-pressed`; anything clickable is a button (the model picker's Retry, the compare cards' actions, the scroll-map markers); tree node actions show on the selected node as well as on hover, so keyboard and touch reach them; the composer's actions (Attach, Edit & fork, Deliberate, Debate, Redirect, Send) carry visible text labels at every width — below `sm` the status line takes its own row and the actions wrap under it (`e2e/tests/responsive.spec.ts` checks the labels and that nothing leaves the toolbar at 390 and 820px); an unavailable composer action is `aria-disabled`, not `disabled`, so it stays focusable and its tooltip says why from the keyboard too; information is never only in `text.disabled`.
- **Never ask the user to read a raw model ID**, including composite labels: `MessageBubble` uses `model_name` or `modelLabel`, never a reshuffled ID.
- **Corner radii come from one scale.** `theme.shape.borderRadius` is MUI's 4px, so an `sx` radius `n` is n × 4px (3 = 12px, cards and bubbles); radii set outside `sx` (inline styles, React Flow nodes, `globals.css`) use `RADIUS` from `theme.ts` (sm 6, md 8, lg 12, panel 16). The base used to be 16px, which made `borderRadius: 2` 32px and every panel a pill.
- **Pixel sizes in `sx` are strings.** A number from 0 to 1 for `width`/`height` (and their min/max) is a fraction: `height: 1` is 100%. The diff view's visually hidden labels had it, so each was as tall as the transcript and a debate's "Show changes" left thousands of blank pixels below it (`AnswerDiff.test.tsx` checks they stay 1px).
- **The scroll map** (`ChatView`, `nav` "Jump to a message"): one marker per message, placed where the scrollbar thumb sits when that message is at the top, and a click smooth-scrolls there. A jump holds the transcript's follow-the-stream off until it lands (`jumping`, cleared on `scrollend` or after 1.5 s): its first frames are still within 50px of the bottom, and the next token used to snap the view back. `e2e/tests/scrollmap.spec.ts` covers it, the jump during a stream included.
- **Theme state has one owner**: `ThemeRegistry.tsx`, exposed via `useThemeMode()`. Do not reintroduce a second `isDark` anywhere (AppHeader and ConfirmDialog read it from the hook). Until the person uses the toggle it follows the system's `prefers-color-scheme` (so Playwright, which emulates light, now runs the e2e suite in the light theme).
- **localStorage hydration** goes through `hooks/useStoredValue.ts` (`useSyncExternalStore`). A `useState` + mount effect trips `react-hooks/set-state-in-effect`; a lazy `useState` initializer mismatches SSR.
- `LANE_WIDTH` (300) and `ROUND_HEIGHT` (160) exist in `services/tree.py` and `hooks/useDebateTree.ts` (the canvas overlays import the latter). Change both together or optimistic pending nodes land on top of real ones.
